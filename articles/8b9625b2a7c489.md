# はじめに

OBSは非常に高機能ですが、個人開発でゲーム配信をしながら使うと、設定項目の多さや拡張機能の管理、ゲーム側との負荷配分が気になる場面があります。

そこで現在、Rust製の軽量配信ソフト **Yaoyorozu Stream** を開発しています。

目標はかなり単純です。

- 起動して迷わず使える
- 重いゲームを遊びながらでも安定する
- 録画と配信を同じ操作感で扱える
- PC音声、マイク、アプリ音声を個別に制御できる
- ワイプやクロマキーなど、配信でよく使う機能を最初からまとめて入れる
- プレビューで見えているものと、本番の配信・録画結果がずれない

今回は、YouTubeへの実配信が成立し、音声Mix、ウィンドウ単位のキャプチャ、リアルタイム音声調整、オーバーレイ合成の入口まで進んだので、一度ここで開発記録としてまとめます。

# 開発環境

現在の構成は次のようになっています。

- 言語: Rust
- UI: eframe / egui
- 映像キャプチャ: Windows Graphics Capture (WGC)
- 音声キャプチャ: WASAPI
- 配信・録画処理: FFmpeg
- 配信先: YouTube / Twitchを想定したマルチプラットフォーム構成
- 対象OS: Windows 11

配信ソフトは映像、音声、UI、録画、ネットワーク送信が同時に動くので、GCによる停止がないRustは相性が良いと感じています。

もちろん「Rustだから自動的に軽い」わけではなく、実際にはフレームコピー回数、GPUとCPU間の転送、バッファ設計、スレッド構成の方が効いてきます。そのため、軽量化は言語だけに頼らず、経路そのものを短くする方向で進めています。

# ここまで実装できたこと

## YouTubeへの実配信

YouTube Liveへ実際に映像を送れるところまで到達しました。

途中では、ソフト側では「送信中」と表示されているのに、YouTube Studio側ではデータ未受信という状態も発生しました。

この問題を切り分けながら、以下を修正しています。

- YouTube向けRTMP / RTMPSの扱い
- H.264の出力条件
- 2秒GOPを意識したキーフレーム設定
- CBR寄りのレート制御
- yuv420p出力
- AAC音声トラック
- FFmpeg stderrの診断表示
- 「FFmpegプロセスが動いている」と「YouTube側で受信できている」を同一視しない状態設計

現在はYouTube Studio側まで映像が届き、実配信テストができる状態になっています。

## PC音声・マイク・アプリ音声のMix

音声はWASAPIを使い、次の単位で扱えるようにしています。

- PC音声
- マイク
- アプリ音声

各チャンネルには、

- Gain
- Mute
- 配信Mix参加 ON / OFF
- 個別WAV保存 ON / OFF

を持たせています。

個別WAVは原音を残し、GainやMuteは非破壊で扱う構成です。

さらに、配信中にPC音声やマイクのGain、Mute、Master Gainを変更しても、その変更がそのままYouTube側へ反映されるところまで確認できました。

これはかなり大きな前進でした。

## 個別WAVと録画

録画時にはPC音声やマイクを個別WAVとして保存できます。

保存OFFの場合は、Mix処理に必要な一時WAVだけ内部で使い、完成MP4生成後に自動削除するようにしています。

一度、一時WAVの診断用 `*.audio.txt` だけが残る不具合もありましたが、WAVと診断ファイルをまとめて削除するように修正しました。

# 実際に踏んだバグ

今回の開発では、配信ソフトらしいバグをかなり踏みました。

## 1. プレビューはゲームなのに、配信はデスクトップ

ゲームウィンドウを選択すると、プレビューには正しいゲーム画面が表示されるのに、YouTube側にはデスクトップ全体が送られる不具合がありました。

原因は、プレビュー側ではWGCを使っているのに、配信側ではFFmpegが別経路で画面を取り直していたことでした。

タイトル文字列に依存すると、日本語、中国語、記号、タイトル変更などにも弱くなります。

そこで、配信側でも **WGCで実際に選択したフレームをそのまま使う** 方向へ変更しました。

これにより、原神のような日本語タイトルのゲームでも、選択したウィンドウをそのまま配信できるようになりました。

表示名は文字列でよくても、内部識別はHWND / PID / exeのような実体ベースにする方が安全だと実感しました。

## 2. YouTubeから「受信している動画が少ない」と警告された

映像自体は届いているのに、YouTube Studio側で次の警告が出ました。

> YouTube が受信している動画が少ないため、滑らかなストリーミングを維持できません。

このとき、1080p60で配信している一方、配信用に流用していたWGCのプレビューreadbackは十分な頻度でフレームを供給できていませんでした。

そこで、最新フレームを保持し、設定FPSに合わせて一定間隔でFFmpegへ渡すフレームペーシングを追加しました。

新しいフレームがまだ来ていない場合は、直前フレームを複製して送信間隔を維持します。

この修正後、YouTube側の警告は出なくなりました。

この経験から、ライブ配信では「エンコーダ設定が正しい」だけでなく、**入力フレームが安定した周期で供給されること**も非常に重要だと分かりました。

## 3. 録画だけアスペクト比がずれる

配信映像は正しいのに、録画したMP4だけ縦横比が崩れる問題も出ました。

原因は、入力ウィンドウの比率を無視して、録画側で1920×1080へ強制的に合わせていたことでした。

修正方針は、

1. 入力のアスペクト比を維持
2. 1920×1080の範囲内に収める
3. 余った部分のみ余白を入れる
4. SARを1:1へ固定

という形です。

修正後、録画映像の比率が正しくなったことを確認できました。

ここは今後さらに重要で、最終的には

```text
映像ソース
   ↓
共通コンポジタ
   ├─ プレビュー
   ├─ 配信
   └─ 録画
```

という構造に寄せたいと考えています。

プレビュー、配信、録画で別々の映像を作ると、どうしても「見た目と本番が違う」問題が起きやすいためです。

# 原神で実配信テスト

ウィンドウ選択の検証には原神を使いました。

原神はテスト対象としてかなり便利でした。

- 日本語タイトルを含む
- ランチャーとゲーム本体でウィンドウが分かれる
- 動きのある3Dゲーム
- UIが細かい
- ゲーム音声がある
- 1080p60の確認がしやすい

実際に、

- 選択したゲームウィンドウをYouTubeへ送信
- PC音声を送信
- マイク音声を送信
- 配信中に音量設定を変更
- YouTube側で変更が反映される
- 「受信している動画が少ない」警告なし

まで確認できました。

# ゼンレスゾーンゼロもテスト対象へ

次の実戦負荷テストにはゼンレスゾーンゼロを使っています。

ゼンゼロはアクション比重が高く、戦闘中のカメラ移動やエフェクトも多いため、配信ソフトの負荷試験に向いています。

現時点ではWGCでゼンゼロのウィンドウを選択し、オーバーレイ合成基盤まで動作確認できています。

今後は、

- 1080p60配信
- 音声Mix
- オーバーレイ
- 録画同時実行

をまとめて動かし、ゲーム側FPS、配信drop、音ズレ、安定性を確認していく予定です。

# 音量が小さい問題はソフト側ではなかった

テスト中、一度「配信音声がかなり小さい」という現象がありました。

ログ上でもデスクトップ音声のピークがかなり低く出ていたため、WASAPIやMix処理の不具合を疑いました。

しかし切り分けた結果、原因はYaoyorozu Streamではなく、普段使っているSound BlasterとWindowsマスター音量側が非常に低い設定になっていたことでした。

普段のリスニング環境では小音量で聞いているため、配信用信号まで小さくなっていました。

この問題は配信ソフト側で独立したブーストやモニター音量分離を持つ価値がある、という次の課題にもつながっています。

# ワイプ / オーバーレイ基盤

現在はPhase 9.4系として、ワイプやVtuber表示を見据えたオーバーレイ機能に入っています。

最初のテスト素材は、内蔵の「跳ねるししゃも」です。

今は、

- X位置
- Y位置
- サイズ
- ぴょんぴょん動作ON / OFF

を持たせ、ゲーム映像の上に合成できるところまで進めています。

今後はここを、

- カメラ映像
- 画像
- 別ウィンドウ
- Vtuberソフト
- クロマキー
- 透過ウィンドウ

へ拡張する予定です。

理想は、設定画面を何枚も開くのではなく、

```text
＋ソース
↓
カメラ / ウィンドウ / 画像を選ぶ
↓
プレビュー上に出る
↓
ドラッグして配置
```

くらいの操作で終わることです。

# UIもかなり作り直した

機能追加を続けると、当然UIも混雑してきました。

最初は説明文が小さすぎて読みにくく、文字サイズを上げると今度は画面高さが足りなくなりました。

そこから、

- 説明文の文字サイズ拡大
- 音声パネルの2列化
- 映像ソースをプレビュー下へ移動
- シーンパネルを固定表示
- 上部ステータスバーを下部へ移動
- 詳細情報を折りたたみ化

などを行い、かなり実用的な配置になってきました。

「スクロールすれば見える」ではなく、**よく使うものは最初から見えている**ことを優先しています。

# 配信者が求めているものと、今後の方向

配信者が配信ソフトに求めるものを整理すると、特に重要なのは次の4点だと考えています。

1. 迷わないUI
2. プラグインを増やさなくても主要機能が揃うこと
3. 重いゲームでも邪魔をしない軽さ
4. プレビューと本番結果がずれないこと

Yaoyorozu Streamも、この4点を中心に今後の優先順位を決めています。

次の開発予定は、

- ワイプをマウスで追加・移動・拡縮
- クロマキー / 透過ソース
- カメラ / Vtuberウィンドウ取り込み
- シーン保存とワンクリック切替
- fps / drop / dup / bitrate / speedなどの送信統計表示
- 原神 / ゼンゼロでの長時間安定テスト

です。

# おわりに

最初は「Rustで軽い配信ソフトを作れないか」というところから始まりました。

今はすでに、

- YouTubeへ実配信
- ゲームウィンドウの選択配信
- PC音声 / マイクMix
- 配信中のリアルタイム音量変更
- 録画
- 個別WAV
- オーバーレイ合成

まで動くようになっています。

その一方で、実際にゲームを配信してみないと見つからない問題もかなり多くありました。

デスクトップしか映らない、YouTubeからフレーム不足と言われる、録画だけ比率がずれる、といった問題を一つずつ潰しながら、少しずつ「本当に使える配信ソフト」に近づいています。

今後は、軽さだけではなく、**迷わず使えて、見たままがそのまま配信・録画に出ること**を重視して開発を続けます。

次回は、ワイプ / クロマキー / Vtuber系の取り込みと、ゼンレスゾーンゼロを使った負荷試験あたりを書ければと思います。
