# 日本語で書きやすく、Rustで堅牢に。8g言語を育てたい理由

Rust +
Bevyを土台に、日本語でゲームロジックを書ける独自スクリプト言語「8g」を作っています。

開発を進めながら考えているのは、単に「英語の命令を日本語へ翻訳した言語」にしたいわけではない、ということです。

目標にしているのは、

**英語がプログラミング学習の壁になっている日本語話者が、余計な翻訳作業をせずにゲーム制作へ入れる言語**

です。

そして、書く側はPHPのように気軽に、裏側はRustの強みを使って堅牢にしたいと考えています。

------------------------------------------------------------------------

## 「英語が読めない」が最初の壁になる

プログラミングでは、実際の考え方を学ぶ前に英単語が大量に登場します。

たとえばゲーム開発なら、

``` text
spawn
load
state
query
resource
event
```

といった単語があります。

もちろん慣れてしまえば問題ありません。

しかし、これからプログラミングを始める日本語話者にとっては、

``` text
英単語の意味を調べる
↓
APIの意味を理解する
↓
文法を覚える
↓
ようやく作りたい処理を書く
```

という段階が発生します。

ここで「自分にはプログラミングは難しい」と感じてしまう人もいるはずです。

でも、本当に理解したかったのは英語ではありません。

変数、条件分岐、イベント、状態、ゲームロジックといった**プログラミングそのものの考え方**です。

そこで8gでは、この間にある翻訳作業をできるだけ減らしたいと考えています。

------------------------------------------------------------------------

## 日本語で意味を直接読めるようにする

たとえば8gでは、こんなコードを目指しています。

``` text
（体力） = 100;

もし（（体力） <= 0）{
    「ゲームオーバー」を表示;
}
```

日本語話者なら、まだ8gの細かな仕様を知らなくても、

「体力が0以下ならゲームオーバーを表示するんだな」

と、おおよその意味を推測できます。

イベントも、

``` text
「始める」が押された時{
    「キャラクター選択画面」へ移動;
}
```

のように書ければ、

``` text
ボタンが押される
↓
画面を移動する
```

という処理を、日本語の思考にかなり近い形で記述できます。

8gで重視したいのは、**読める・意味を推測できる・すぐ試せる**ことです。

------------------------------------------------------------------------

## 学習コストを減らしたい

8gで狙っているのは、プログラミングそのものを簡単なものに見せることではありません。

条件分岐には条件分岐の考え方がありますし、変数には変数の考え方があります。

ゲームを作れば、状態管理やイベント処理も必要になります。

そこは学ぶ必要があります。

減らしたいのは、その手前にあるコストです。

``` text
英語を覚える
↓
API名を覚える
↓
文法を覚える
↓
ゲームを作る
```

ではなく、

``` text
日本語なので意味を推測できる
↓
文法とプログラミングの考え方を覚える
↓
ゲームを作る
```

にしたい。

つまり8gは「何も勉強しなくても使える言語」ではなく、**日本語話者が本当に必要な部分へ早く到達するための言語**として育てたいと思っています。

------------------------------------------------------------------------

## PHPのような「こう書けたら楽」を大切にする

8gの書き味は、PHPをかなり参考にしています。

理由は単純で、私自身が書き慣れているからです。

PHPには、

「Webでこれをやりたいなら、こう書けば動く」

という目的への近さがあります。

8gも、ゲームエンジンという用途をある程度固定する代わりに、

``` text
表示
読み込み
生成
削除
移動
保存
再生
停止
取得
設定
同期
```

といったゲーム制作で頻繁に使う処理を、最初から言語とエンジンの共通語彙として持たせたいと考えています。

たとえば、

``` text
「川越宿場町」を読み込み;
「プレイヤー」を生成;
「戦闘BGM」を再生;
```

と書いたら、エンジン側がそれを理解して動く。

用途をゲーム制作に寄せることで、汎用言語とは違う書きやすさを作れないか、という考えです。

そして言語仕様も、最初から完璧なものを決めるのではなく、

``` text
実際に8gでゲームを書く
↓
「ここ、もっとこう書きたい」と感じる
↓
構文を改善する
↓
また実際に使う
```

という形で育てていきたいと思っています。

------------------------------------------------------------------------

## 表は書きやすく、裏はRustで堅牢に

8gの実装側にはRustを使っています。

Rustの魅力の一つは、型の不整合や所有権・借用に関する問題など、多くの危険な状態をコンパイル時に検出できることです。

もちろんRustを使えばバグがなくなるわけではありません。

それでも、危険な状態をなるべく早い段階で弾くという思想は、8gとも相性がいいと感じています。

構造としては、

``` text
8g
│
│ 日本語で書きやすい
│ PHPのように目的へ近い書き味
▼
8g Parser / Runtime
│
│ 構文・変数・値・命令を検証
▼
Rust
│
│ エンジン側を堅牢に実装
▼
Bevy
```

という形です。

つまり、

**表側は軽く、裏側は堅く。**

これを8gの特徴にしたいと思っています。

------------------------------------------------------------------------

## PHPの「緩さ」まで真似する必要はない

PHPの書きやすさは参考にしたい一方で、型や値の扱いまで同じにする必要はありません。

たとえば、

``` text
（体力） = 「いっぱい」;
（体力） -= 10;
```

というコードがあったとします。

この場合、実行してから不可解な挙動になるのではなく、8g側で事前に検査して、

``` text
8gエラー:
（体力）は文字列です。
数値の「10」を引くことはできません。

2行目:
（体力） -= 10;
```

のように、日本語で原因を説明できるようにしたい。

同様に、

``` text
（体力）が見つかりません。
「体力」を先に設定してください。
```

や、

``` text
「キャラクター選択画面」は登録されていない画面です。
```

のように、エラーそのものも日本語話者が読んで理解できることを重視したいです。

英語のエラーメッセージを検索して、その意味を翻訳するところからデバッグが始まる状態も、できるだけ減らしたいと考えています。

------------------------------------------------------------------------

## Rustは「日本語とエンジンの翻訳役」

8gでは、Rustにゲーム内容そのものを書き続ける構造にはしたくありません。

現在目指しているのは、

``` text
.8g
↓
8g Parser
↓
8g Runtime
↓
Rust Bridge
↓
Bevy
```

という構造です。

ゲームの内容は8gで書きます。

Rustはそれを解析し、

「これは画面を表示する命令」 「これはStateを変更する命令」
「これはキャラクターを生成する命令」

と判断してBevyへ渡します。

つまりRustは、**日本語で書かれたゲームロジックとゲームエンジンの間に立つ翻訳役**です。

------------------------------------------------------------------------

## 将来はゲーム以外にもBridgeを作れるかもしれない

8gは現在ゲームエンジンを中心に開発しています。

ただ、ランタイムとBridgeを分離できれば、将来的には別の実行環境へ接続することも考えられます。

たとえばWebなら、

``` text
              ┌→ Rust Bridge → Bevy
              │
.8g → Runtime ┤
              │
              └→ JavaScript Bridge → Web
```

という構造です。

Web側ではJavaScriptがDOMや`fetch`などへの橋渡しを担当します。

そうなれば、

``` text
（記事） = 「posts/news.md」を読み込み;
（記事）を表示;
```

という8gコードを、Web向けBridgeがブラウザの処理へ変換する、といったことも考えられます。

現在運営している開発サイトもMarkdownベースなので、将来的には自分のサイトのCMS制御を8gで書く、という実験もしてみたいと思っています。

------------------------------------------------------------------------

## 「日本人が作った言語」ではなく「日本語話者のための言語」

日本人が作った有名なプログラミング言語にはRubyがあります。

Rubyは世界中で使われている素晴らしい汎用言語です。

一方で8gが目指したい立ち位置は少し違います。

8gでは最初から、

**日本語話者が日本語の感覚で読み書きできること**

を設計上の中心に置きたい。

英語圏へ合わせることを最優先にはせず、

``` text
もし
表示
読み込み
生成
押された時
```

のような、日本語として意味が伝わる語彙を中心にします。

「英語が苦手だからプログラミングは無理」

ではなく、

「英語は苦手だけど、プログラミングの考え方なら分かる」

という人が入ってこられる場所を作れたらと思っています。

------------------------------------------------------------------------

## 8gを育てる上で大切にしたいこと

現時点で、8gの設計について大切にしたいことはかなり明確になってきました。

-   日本語として読める
-   意味を推測しやすい
-   PHPのように目的へ近い書き味
-   ゲーム制作でよく使う機能を標準化する
-   エラーも日本語で説明する
-   書く側にRustやBevyの都合を押し付けすぎない
-   実際に使って「こう書きたい」と感じたものから言語を育てる
-   実装側ではRustの堅牢さを活用する

一言でまとめるなら、

> **書きたい日本語を先に決めて、Rustを後から合わせる。**

という考え方です。

------------------------------------------------------------------------

## おわりに

8gはまだ開発初期です。

現在ようやく、`.8g`
ファイルをRustが直接読み込み、構文を解析し、BevyのStateやUIへ命令を渡せるところまで進みました。

ここから変数、条件分岐、イベント、関数、型検査、エラー表示などを育てていく必要があります。

それでも方向性は少しずつ見えてきました。

**PHPのように書きやすく、日本語で意味が分かり、Rustを土台にできるだけ堅牢にする。**

そして、英語がプログラミングへの壁になっている日本語話者の学習コストを少しでも減らす。

いつか8gを使った人から、

「英語のAPIは難しかったけど、これならゲームを作れた」

と言ってもらえる言語になったら、とても嬉しいです。
