## はじめに

Rust + Bevy
で、和風MMO向けの自作ゲームエンジン「八百万エンジン」を開発しています。

このエンジンでは、ゲーム側のスクリプトを Rust
で直接書くのではなく、**日本語でゲームの指示を書ける独自言語 `.8g`**
を用意する構想があります。

目標は Godot における GDScript のように、

-   ゲーム内容は `.8g`
-   `.8g` を Rust が解釈する
-   Rust が Bevy の機能へ橋渡しする
-   `.8g` を追加・変更するたびに Rust コードを生成しない
-   ゲームスクリプトを書くために英語のAPI名を大量に覚えなくてよい

という構造です。

今回、その初期実装が想定からズレていることに気づき、パーサーと Bevy
側の役割を整理し直しました。

この記事では、**Rustコード生成型になっていた `.8g`
を、実行時に直接解釈するランタイム方式へ変更し、Bevy の State と UI
遷移まで通したところ**までをまとめます。

------------------------------------------------------------------------

## 目指している構造

最終的に目指しているのは、次の流れです。

``` text
.8g
 ↓
Rust Parser
 ↓
AST / 命令 / 式
 ↓
8g Runtime
 ↓
Rust Executor / Engine API
 ↓
Bevy
```

Rust の役割は「ゲームそのものを書くこと」ではありません。

**日本語の `.8g` を Bevy が理解できる処理へ翻訳する役**です。

たとえばゲーム側では、

``` text
（体力） = 100;

もし（（体力） <= 0）{
    「ゲームオーバー」を表示;
}
```

のように書きます。

Rust はこれを、

``` text
変数「体力」に100を代入
↓
体力 <= 0 を評価
↓
真なら「ゲームオーバー」を表示
↓
Bevy UIへ命令
```

という形で解釈します。

------------------------------------------------------------------------

## なぜ作り直すことになったのか

初期実装でも `.8g`
らしき日本語スクリプトから処理を作るところまでは進んでいました。

しかし、実際には、

``` text
.8gを書く
 ↓
対応するRustコードを生成
 ↓
cargo build
 ↓
実行
```

という方向へ寄っていました。

これでは `.8g` を追加するたびに Rust のコンパイルが必要になります。

それでは「ゲーム用の独自スクリプト言語」を作った意味が薄くなってしまいます。

欲しかったのは、

``` text
.8gを書く
 ↓
保存
 ↓
Rustランタイムが直接読む
 ↓
解析
 ↓
そのままBevyへ渡す
```

という仕組みです。

ゲーム内容を変更するだけなら Rust を再生成しない。

Rust
の再コンパイルが必要なのは、**8g言語そのものに新しい機能を追加した場合や、エンジンAPIを増やした場合**だけ、という境界を目指します。

------------------------------------------------------------------------

## 8gの基本構文

書き味は、自分が慣れている PHP にある程度寄せたいと考えています。

ただし、日本語で読み書きしやすいことを優先します。

現在検討している基本ルールは次の通りです。

``` text
「文字列」        → 文字列リテラル
（変数名）        → 変数
=                 → 代入
== / ===          → 比較
!=                → 不一致
<= / >=           → 比較
{ }               → ブロック
;                 → 文末
```

例：

``` text
（名前） = 「大和」;
（体力） = 100;

もし（（体力） <= 0）{
    「ゲームオーバー」を表示;
}
```

### 「」の中はすべて文字列

重要なルールとして、

``` text
「キャラクター（K）」
```

は全体を文字列として扱います。

外側が `「」` なら、その中に `（）` があっても変数として解析しません。

一方、

``` text
（キャラクター）
```

なら変数です。

これによって Rust
側が文脈から「これは文字列なのか変数なのか」を推測する必要を減らせます。

------------------------------------------------------------------------

## Rust側をランタイム方式へ変更

以前の命令構造は、概念的には、

``` rust
命令 {
    動詞,
    引数: String,
}
```

という単純な形でした。

しかし、これだけでは変数・数値・比較式・条件分岐などを扱うには不足します。

そこで、ランタイム側を次のような責務へ分ける方向に変更しました。

``` text
Value
 ├─ 文字列
 ├─ 数値
 ├─ 真偽値
 └─ なし

Expression
 ├─ 値
 ├─ 変数参照
 ├─ 演算
 └─ 比較

Statement
 ├─ 代入
 ├─ 命令
 └─ 条件分岐
```

そして、

``` text
parser_jp.rs
 ↓
Expression / Statement
 ↓
runtime.rs
 ↓
executor.rs
 ↓
Bevy
```

という流れにします。

ポイントは、**Rustソースコードを生成するのではなく、Rustプログラム自身が
`.8g` を読み、構文を評価すること**です。

------------------------------------------------------------------------

## mainSystem.8gを直接読み込む

変更後は起動時に `.8g` ファイルを直接読み込むようにしました。

対象は現在、

``` text
crates/yamato_crafttowers/jascript/mainSystem.8g
```

です。

実行ログでは、

``` text
【八百万駆動】8gランタイムを起動します
【8g読込】crates/yamato_crafttowers/jascript/mainSystem.8g
【8g解析成功】12 文
```

まで到達しました。

さらに executor 側まで処理が流れ、

``` text
【8g】八百万システムを初期化。
【8g開始】ゲーム起動
【8g初期化】ゲーム
【8gロード】ゲームタイトル画面
【8g表示】ロードバー
【8gスポーン】キャラクター（K） -> 地点情報
【8g表示】ロード完了
【8g】起動スクリプトの実行が完了しました
```

というログが出ました。

ここでようやく、

``` text
.8g
 ↓
Rustが読む
 ↓
Rustが解析する
 ↓
Rustが実行する
```

という独自言語としての基本経路が通りました。

------------------------------------------------------------------------

## Bevy側も「翻訳先」として整理する

次に問題になったのが `yaoyorozu_beby` 側です。

最初の実行では、

``` text
State yaoyorozu_core::GameFlowState is already initialized.
```

という警告が出ていました。

State
が複数箇所から初期化されていたため、初期化責務を1箇所へ整理しました。

さらに `.8g` から、

``` text
キャラクター選択画面
```

という日本語の状態名が送られてきたとき、Bevy 側では認識できず、

``` text
【八百万状態遷移】 未知の状態: キャラクター選択画面
```

となっていました。

そこで Rust 側に、日本語のゲーム用名称から `GameFlowState`
への翻訳を持たせました。

概念的には、

``` rust
match state_name {
    "タイトル画面" => GameFlowState::Title,
    "キャラクター選択画面" => GameFlowState::CharacterSelection,
    "ロード画面" => GameFlowState::Loading,
    "ゲーム画面" => GameFlowState::Gameplay,
    "設定画面" => GameFlowState::Settings,
    _ => { /* unknown */ }
}
```

という役割です。

その結果、

``` text
【八百万状態遷移要求】 キャラクター選択画面
【遷移】 CharacterSelection へ遷移中...
```

まで通るようになりました。

------------------------------------------------------------------------

## 同じStateへの再遷移も防ぐ

`.8g` と Bevy の双方から状態遷移要求が来る途中段階だったため、

``` text
Title → Title
```

という不要な再遷移も起こり得ました。

そこで現在の State と遷移先が同じなら、

``` text
【八百万状態遷移】 現在の状態と同一のため維持: Title
```

として遷移しないようにしました。

これでタイトルUIの不要な再生成を防げます。

------------------------------------------------------------------------

## UI cleanupで二重despawnが発生

State 遷移が通るようになると、次は UI の破棄処理で問題が見つかりました。

ログには、

``` text
Entity despawned: The entity with ID ... is invalid
```

という警告が複数出ました。

原因はタイトル画面を識別するマーカーを、UIルートだけでなく子Entityにも付け、終了時にそれらをまとめて
`despawn()` していた構造でした。

親を削除すれば階層下の子も破棄されるのに、その子へさらに `despawn()`
が予約されていました。

そこで、

``` text
Title UI Root  ← OnTitleScreen
 ├─ Image
 ├─ Button
 ├─ Button
 └─ Button
```

のように、**画面マーカーをルートだけに付ける**形へ変更しました。

State 終了時はルートだけ削除します。

修正後、`Entity despawned` 警告は消えました。

------------------------------------------------------------------------

## ところが画面が真っ黒になった

cleanup が正常になると、今度は `CharacterSelection`
遷移後にウィンドウが真っ黒になりました。

これは cleanup 自体の失敗ではなく、むしろ逆でした。

タイトル画面に紐付いていた `Camera2d`
まで正しく削除され、次の画面側に描画用Cameraが存在しなくなったためです。

そこでUIのCamera設計も変更しました。

------------------------------------------------------------------------

## UI CameraをStateから分離する

修正前のイメージは、

``` text
Title
 ├─ Camera2d
 └─ Title UI

Title終了
 ↓
Camera2dも削除
 ↓
CharacterSelection
 ↓
Cameraがない
 ↓
黒画面
```

でした。

これを、

``` text
Shared UI Camera
  ↑
  └─ アプリ起動時に1回生成して常駐

Title
 └─ Title UI Root

CharacterSelection
 └─ CharacterSelection UI Root
```

へ変更しました。

Camera は State に所属させません。

各 State が所有するのは UI Root だけです。

``` text
OnEnter(Title)
    → Title UI生成

OnExit(Title)
    → Title UI Root削除

OnEnter(CharacterSelection)
    → CharacterSelection UI生成

OnExit(CharacterSelection)
    → CharacterSelection UI Root削除
```

この方式なら、今後 `Loading`、`Gameplay`、`Settings`
と画面が増えても、Cameraを毎回生成・削除する必要がありません。

## 次の課題：遷移の判断も8g側へ戻す

現在はまだ一つ大きな暫定処理があります。

起動スクリプトが CharacterSelection
への遷移要求まで出しているため、タイトル画面表示後に自動的にキャラクター選択画面へ進みます。

本来ほしい動作は、

``` text
ゲーム起動
 ↓
タイトル画面
 ↓
ユーザー入力待ち
 ↓
「始める」ボタン
 ↓
CharacterSelection
```

です。

当面は `mainSystem.8g`
の自動遷移を外し、Rust側のタイトルボタン処理から、

``` rust
next_state.set(GameFlowState::CharacterSelection);
```

を呼べば期待する操作にはできます。

ただし、これも最終形ではありません。

目標は、

``` text
ユーザーが「始める」を押す
 ↓
Bevyが入力を検出
 ↓
Rustが8gランタイムへ
「始めるが押された」
というイベントを渡す
 ↓
.8gが次の処理を判断
 ↓
「キャラクター選択画面」へ移動
 ↓
RustがGameFlowStateへ翻訳
 ↓
Bevyが遷移
```

という構造です。

つまり Rust に、

``` text
Startボタンを押したらCharacterSelection
```

という**ゲーム固有の判断を置かない**ようにします。

Rust
は入力を受け取り、日本語スクリプトへイベントとして渡し、返ってきた命令を
Bevy へ橋渡しするだけです。

## MMO向け機能との関係

この `.8g` の仕組みは、単に日本語で `if`
が書けることだけが目的ではありません。

Bevy
にはゲームエンジンとしての土台がありますが、自作MMOで必要になる機能はエンジン側で用意していく必要があります。

たとえば、

``` text
ワールド管理
プレイヤー同期
永続化
クエスト
インベントリ
交易
経済
NPC
階層管理
```

などです。

これらの基盤を Rust で実装し、8gランタイムへ公開できれば、ゲーム側では、

``` text
「川越宿場町」を読み込み;
「姉はつらいよ」を開始;
（プレイヤー）を同期;
```

のような日本語スクリプトから利用できるようになります。

そのため、役割分担は次の形を目指しています。

``` text
.8g
    ゲーム内容・ゲームロジック
            ↓

Rust / 8g Runtime
    日本語の解析・翻訳・実行管理
            ↓

八百万エンジンAPI
    MMO機能・ゲーム共通機能
            ↓

Bevy
    ECS・描画・入力・アセット・UIなど
```

ゲームの指示ファイルを `.8g`
で増やしていけるようになれば、Rust側の巨大化を抑えながらゲーム内容を追加できます。

## 今回できたところ

今回の作業で、少なくとも次のところまで確認できました。

-   `.8g` ファイルを Rust が直接読み込める
-   `.8g` を Rust コードへ変換しなくても解析できる
-   解析結果を executor まで渡せる
-   日本語の State 名を Bevy の `GameFlowState` へ変換できる
-   同一 State への不要な再遷移を防げる
-   Title UI の生成・cleanupができる
-   UI階層の二重 `despawn` を解消できる
-   UI用 `Camera2d` を共通化できる
-   `Title → CharacterSelection` の State 遷移が通る
-   CharacterSelection UI の生成まで到達できる

まだ言語処理系としては入口ですが、最初にズレてしまった「Rustコード生成器」から、**ゲーム実行時に
`.8g` を解釈するランタイム**へ方向を戻せました。

------------------------------------------------------------------------

## 今後

次はまず、

``` text
タイトル画面表示
 ↓
入力待ち
 ↓
ボタンイベントを8gへ渡す
 ↓
8gが遷移を指示
```

を実装する予定です。

その後は変数、条件分岐、イベント、関数、ゲームオブジェクト参照などを少しずつ拡張していきます。

そして Rust 側で MMO 用のエンジン機能を増やし、それを `.8g`
の日本語命令として利用できるようにしていきたいと思っています。

最終的には、

**「RustやBevyの英語APIを直接覚えなくても、日本語のゲームスクリプトをガンガン書いてゲームを作れる」**

ところまで持っていくのが目標です。

まだまだ先は長いですが、ようやく `.8g`
が「独自言語」として動き始めました。
